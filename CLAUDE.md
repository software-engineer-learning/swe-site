# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

MkDocs Material site published at [swe.springlee.dev](https://swe.springlee.dev)
(Cloudflare Pages, Direct Upload via GitHub Actions). Build config lives at the
root (`mkdocs.yml`, `build.sh`, `scripts/`, `docs/index.md`, `docs/SUMMARY.md`);
**content lives under `content/`**.

| Section | Source (edit here) | `docs/` dir | Nav |
| ------- | ------------------ | ----------- | --- |
| LeetCode Algorithms | `content/leetcode-algorithms/` — **git submodule** | `leetcode/` | generated `SUMMARY.md`, converted |
| SWE Interview | `content/swe/` | `swe/` | hand-maintained `SUMMARY.md`, converted |
| System Design | `content/system-design/` | `system-design/` | generated by `scripts/gen_nav.py` |
| Real Interview Questions | `content/real-interview-questions/` | `real-interview-questions/` | hand-maintained `SUMMARY.md`, converted |

Three sections are edited in this repo directly. Only LeetCode is still a separate
repo (submodule), because it has its own GitBook publication, PR workflow and
solution tooling — changes there are made in the submodule and pushed to
`software-engineer-learning/leetcode-algorithms`, not committed here.
`content/leetcode-algorithms/CLAUDE.md` holds that repo's own conventions and its
`/add-solution` skill; read it before editing inside the submodule.

## Critical rule

Everything under `docs/` except `index.md`, `SUMMARY.md`, `javascripts/` and
`stylesheets/` is **generated by `scripts/prepare.sh` and wiped on every run**
(`rm -rf docs/leetcode docs/swe docs/system-design docs/real-interview-questions`).
Never edit content there — edit under `content/` and re-run `prepare.sh`. `site/` is
build output.

## Local development

```bash
git submodule update --init --recursive     # after a fresh clone
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
bash scripts/prepare.sh
.venv/bin/mkdocs serve                      # http://127.0.0.1:8000
```

`prepare.sh` fails loudly if a `content/` source is missing or the submodule is
uninitialised — there is no clone fallback any more.

## Adding a section

1. Put the markdown under `content/<section>/`.
2. `scripts/prepare.sh` — add a `<x>_src` variable and its entry in the existence
   check, add the dir to the `rm -rf` / `mkdir -p` lines, the final page-count
   `find` and the `normalize_fences.py` call, then copy the markdown and emit
   `docs/<section>/SUMMARY.md` via `scripts/convert_summary.py`.
3. `docs/SUMMARY.md` — add the tab; `docs/index.md` — add the section bullet.
4. `README.md` — document the section in the layout table.

Copy blocks exclude the source's own `SUMMARY.md` (it is converted, not copied)
and its `CLAUDE.md` (repo maintenance docs don't belong on the site).

## Gotchas

- Content uses GitBook-style `$$...$$` math, rendered client-side by KaTeX
  auto-render (`docs/javascripts/katex.js`) — not a Python markdown extension.
- Only an exact `README.md` becomes a directory index in MkDocs. `prepare.sh`
  normalises the `Readme.md`/`README.md` mix in `content/system-design` for that
  reason.
- MkDocs skips dot-directories, so the LeetCode submodule's `.gitbook/assets` is
  copied to `_assets/` and the links are rewritten by `sed`.
- Material's search indexes a page under its **first `<h1>`**; the nav label and
  front-matter `title:` are only fallbacks when a page has no h1. Most LeetCode
  `solution.md` files open with `# Intuition` and never name their problem, which
  made them unfindable by number. `scripts/leetcode_titles.py` fixes this at build
  time: it demotes the existing headings, prepends an h1 from the SUMMARY label
  (falling back to the folder name), and cross-links `description.md`
  and `solution.md`. It edits only `docs/`, so the submodule and its GitBook
  publication are untouched. It must skip `#` lines inside code fences — hence a
  Python parser rather than `sed`.
- `content/system-design/` is a **vendored** copy of our fork of the third-party
  [liquidslr/system-design-notes](https://github.com/liquidslr/system-design-notes).
  `gh repo sync` on the fork no longer reaches the site by itself; upstream changes
  must be rsynced into `content/system-design/` and committed. See the README.
- CI runs `git submodule update --remote content/leetcode-algorithms` before
  building, so the site always publishes the newest solutions, then commits the
  bumped pointer back to `main` after a successful deploy. That bot push does not
  re-trigger the workflow — GitHub suppresses triggers for pushes made with the
  default `GITHUB_TOKEN`. So the pointer in `main` normally names the LeetCode
  commit that is live; if a concurrent push beat it, the step warns instead of
  failing and the next run re-derives the bump.
- Because CI commits to `main`, `git pull` before starting local work, or your
  next push will be rejected as non-fast-forward.
- Deploys run from GitHub Actions (`.github/workflows/deploy.yml`), **not** from
  Cloudflare's Git integration — don't also connect this repo in the Cloudflare
  dashboard, or every change builds twice.
- Because of that, a Cloudflare Pages **deploy hook** cannot rebuild this site.
  It has no repo to clone and no build command to run, so it re-serves the assets
  already uploaded and returns `success: true` while the content stays stale.
  Editing `content/swe`, `content/system-design` or
  `content/real-interview-questions` and pushing to `main` rebuilds the site
  normally; `leetcode-algorithms` instead fires `repository_dispatch:
  content-updated` at this repo from its `gitbook.yml` workflow. If a LeetCode push
  didn't reach the site, check that workflow first.

## Verifying a change

```bash
bash scripts/prepare.sh && .venv/bin/mkdocs build --strict
```

Then check the section landed: `ls site/<section>/`.
